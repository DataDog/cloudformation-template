# Datadog AWS Integration

[![Launch Stack](https://s3.amazonaws.com/cloudformation-examples/cloudformation-launch-stack.png)](https://console.aws.amazon.com/cloudformation/home?region=us-east-1#/stacks/quickcreate?param_APIKey=&param_APPKey=&param_CloudSecurityPostureManagement=false&param_DatadogSite=datadoghq.com&param_InstallLambdaLogForwarder=true&stackName=DatadogIntegration&templateURL=https%3A%2F%2Fdatadog-cloudformation-template-quickstart.s3.amazonaws.com%2Faws%2Fv2.0.5%2Fmain_v2.yaml)
  
## Installation

1. Open the [AWS integration tile](https://app.datadoghq.com/account/settings#integrations/amazon-web-services) within the Datadog platform.
   1. Click "Add AWS Account(s)".
   1. Fill out the various fields under "Automatically using CloudFormation".
   1. Click "Launch CloudFormation Template" in the bottom right.
1. Log into your admin AWS account/role and deploy the CloudFormation Stack that you're linked to. All required parameters will be filled in.
   1. Optionally edit "Advanced" fields to set the `IAMRoleName` used, or disable default collection settings.
   1. On a rare occasion, if you already have a stack deployed in the same AWS account using this template (e.g., monitor the same AWS account in multiple Datadog accounts), You MUST use a different role name for `IAMRoleName`.
   1. Check the 2 checkboxes under "Capabilities" to give our stack the necessary permissions.
   1. Click **Create stack**.

## AWS Resources

This template creates the following AWS resources required by the Datadog AWS integration:

- An IAM role for Datadog to assume for data collection (e.g., CloudWatch metrics)
- The [Datadog Forwarder Lambda function](https://github.com/DataDog/datadog-serverless-functions/tree/master/aws/logs_monitoring) to ship logs from S3 and CloudWatch, custom metrics and traces from Lambda functions to Datadog
  - The Datadog Forwarder only deploys to the AWS region where the AWS integration CloudFormation stack is launched. If you operate in multiple AWS regions, you can deploy the Forwarder stack (without the rest of the AWS integration stack) directly to other regions as needed.
  - The Datadog Forwarder is installed with default settings as a nested stack, edit the nested stack directly to update the forwarder specific settings.

## Agent installation launcher (v4.23.0, unreleased)

The Agent installation launcher supports only commercial AWS accounts (`aws`). AWS GovCloud and China are not supported. Create and update requests are rejected in those partitions, including direct template launches; existing launchers can still be deleted. This restriction does not change the initial AWS integration QuickStart.

`main_agent_installation_launcher.yaml` is the entry point for post-setup Agent installation and **Add Permissions**. Each launch uses a unique request-stack name. After one CloudFormation approval, its helper creates or updates the stable `DatadogAgentInstallation` stack automatically; there is no second change-set approval.

- The launcher grants its own helper deployment permissions. It does not require new discovery permissions on the existing Datadog integration role. Reverse ownership lookup by physical resource ID requires the helper's read-only `cloudformation:DescribeStackResources` permission on `Resource: "*"`; stack descriptions and write operations remain resource-scoped. The deploying user must be allowed to create these helper resources; organization policies and permission boundaries still apply. Direct change-set creation is restricted to the launcher's installation-template release. Nested template operations must come through CloudFormation and use the published permissions or forwarding template; earlier releases remain accessible for rollback.
- Creating and managing the EventBridge connection requires delegated Secrets Manager access in addition to the EventBridge service-linked role. The launcher scopes this access to the canonical connection's secret in the deploying account and requires the request chain to start with CloudFormation and end with EventBridge. Direct secret access and unrelated secrets are not granted.
- Existing installation resource types, credentials, parameters, and customer tags are preserved. New requests add resource types; they do not remove previously configured types or rotate the API key. The launcher uses API-key-only forwarding and does not request or pass an application key. When updating older installations, the obsolete `APPKey` parameter is omitted. The selected integration's external ID is passed from Datadog and stored on the installation stack; it cannot be changed by another launcher request.
- Permission refreshes and additive resource-type updates preserve the permissions custom resource's identity. The launcher permits their conditional change-set entries only for the recognized, non-frozen permissions child. Type expansion must match the union of existing and requested types, with matching current-child and proposed-child parameters; removals, unrelated property changes, and actual replacements remain blocked.
- The add-on creates separately named, owner-tagged instrumentation policies. Replacement, rollback, and deletion are restricted to that permissions stack's policy namespace and owner tag. QuickStart's role-wide policies and other add-ons' policies are left alone, including after a failed first creation. All owners' attachments count toward the IAM role's policy quota; insufficient capacity fails before policy replacement.
- Shared permissions boundaries are reused only when their documents match. The add-on does not rewrite a boundary belonging to other owners, claim an unverified boundary, or delete a boundary it never owned. A mismatched shared boundary requires reconciliation by its owner.
- Compatible forwarding owned by QuickStart or another verifiable external setup is left untouched. IAM role ownership is resolved from CloudFormation resource records across enabled regions, not IAM-role tags. The records must match the role's physical name and expected logical resource, identify a unique stable owner, and not predate the current role's creation. Deleted-stack history does not establish ownership; discovery errors are not treated as absence. Its owning root stack must match the selected integration's role name and Datadog site. The external ID is verified from the root parameter or, for manual QuickStart templates, the linked `DatadogIntegrationRoleStack`. The nested role stack must belong to that root and agree with its role and site. Matching endpoints alone are not sufficient; forwarding without a verifiable owner is rejected. Forwarding already owned by the installation stack remains owned by it. The launcher does not update `DatadogIntegration` or adopt external resources.
- Discovery checks enabled regions. An existing installation stays in its region. A new installation uses the forwarding primary region, or `us-east-1` when forwarding is absent or only ECS is configured. ECS-only requests do not read or require healthy EventBridge pipelines, but still check forwarding ownership to avoid creating a second permissions owner. Restricted access to required discovery calls causes a safe failure, not an assumption that resources are absent.
- When a verified external pipeline lacks rules for requested types, `DatadogAgentSupplementaryForwardingStack` is added inside `DatadogAgentInstallation`. Its `datadog_agent_supplementary_forwarding.yaml` template creates uniquely named, owner-tagged primary-region rules and an invocation role scoped to the existing API destination. The shared connection, destination, credentials, cross-region role, and backend-managed regional rules are not changed. This uses the same launcher approval; customers do not launch the supplementary template separately.
- Supplementary rules remain owned by the installation across updates, including if QuickStart later adds overlapping coverage. They are not automatically disabled or transferred to QuickStart. Types with validated supplementary coverage do not depend on QuickStart's corresponding rules; the shared pipeline must still be compatible. Overlapping rules can deliver the same event more than once; no new backend deduplication is introduced. Deleting the installation removes its supplementary rules and invocation role, not the shared pipeline. If the shared pipeline is removed or becomes unusable, dependent supplementary forwarding can stop; the add-on does not repair it.
- Incomplete or incompatible forwarding, multiple installation stacks, unrecognized supplementary-rule ownership, renamed installation owners discovered through forwarding, and conflicting account/role/site settings require review before retrying. Supplementary rules must be in the existing pipeline's primary region; an installation in another region is not automatically moved. These checks validate configuration, not end-to-end event delivery.
- A concurrent request or a stack needing recovery is not overwritten. Wait for the existing operation to finish, or repair it in CloudFormation, then launch a new request. Failed requests never automatically delete an installation stack.
- Unmodified v4.21.1 installation templates can be adopted without renaming `DatadogAgentInstallation` or changing legacy policy ownership. The launcher verifies the original root template against the recorded YAML/JSON fixture, checks the legacy child's parameters, and traces the actual integration role to its QuickStart stack and external ID. The role must have unambiguous matching trust. Other versions, unbound stack-scoped installations, customized templates, and unverifiable owners remain unsupported; no legacy stack is automatically deleted.
- Adoption freezes `DatadogIntegrationPermissionsStack` at its existing v4.21.1 template and resource types. It adds `DatadogAgentInstallationPermissionsStack`, which owns the new isolated policies and receives subsequent resource-type changes and permission refreshes. Legacy grants remain attached and count toward quota. The launcher rejects any nested change-set resource change in the frozen child, including helper updates, removals, and replacements. The new child depends on the legacy child so deletion releases the new boundary owner before legacy cleanup. Direct policy-scope changes remain rejected.
- Adopted installations preserve their existing tags rather than introducing inherited tag updates into the frozen child. The `InstallationTemplateVersion` output records the current release and prevents downgrades. `LegacyPermissionsTemplateVersion` and `LegacyInstrumentationResourceTypes` are internal pins maintained by the launcher, not manual migration controls.
- Extra or incorrectly typed root-stack resources block automatic updates. Before execution, the helper checks every page of the root and nested change sets and rejects removals, replacements (including conditional replacements), or incomplete previews. The sole conditional-replacement exception is an update to only `InstrumentationRefreshToken` on the known permissions custom resource in a direct, non-frozen permissions child; its handler preserves the existing physical resource ID. Other conditional changes still require manual review in CloudFormation rather than an automatic update. The checks cover CloudFormation resource changes, not every IAM mutation performed inside Lambda custom resources.

The launcher's **Outputs** tab links to the installation stack and reports its deployment result. The launcher waits for the specific installation operation to finish; opening AWS or creating a change set is not treated as successful installation. The initial AWS review shows the launcher resources and authorizes it to apply downstream changes automatically, not a complete downstream resource or IAM-policy diff.

A failed first change set can leave the target in `REVIEW_IN_PROGRESS`. A fresh launcher cannot resume that earlier request, and deleting the failed launcher does not remove the target. The failure reason links directly to the target stack even when launcher Outputs are unavailable. If the original launcher is still running, wait. If it failed or was deleted, inspect its change sets and resources; delete the target only after confirming the earlier launch has stopped and no resources were deployed, then retry. Never delete an active or populated installation as a generic retry step.

Deleting a launcher does **not** uninstall the installation. A launcher whose latest deployment completed successfully can be deleted without waiting for another launcher's installation update. An unfinished or failed launcher still waits for an active installation operation to settle before removing helper resources that may be in use. Delete `DatadogAgentInstallation` separately when intentionally removing its resources. Forwarding owned by another stack is unaffected by deleting the installation. For adopted legacy installations, both permissions children have normal deletion behavior: the old helper can remove role-wide instrumentation grants shared with QuickStart. Treat installation deletion as intentional offboarding, not removal of only the new permissions manager. The installation's `LegacyPermissionsNotice` output makes this explicit; no nested stacks are retained automatically.

Publish the launcher and installation templates together with `release.sh` before enabling the web-ui links. Validate the deployer's IAM permissions, create/update/rollback behavior, and asynchronous completion in an AWS sandbox before production release.

## Updating your CloudFormation Stack

As of v2.0.0 of the aws_quickstart template updates to the stack parameters are supported. Updates should generally be made to the root CloudFormation Stack (entitled DatadogIntegration by default). We do not support updating the API Key or APP Key fields to point to a different Datadog Organization - if these are updated they must point to the original Organization. You can also update the version of the template used by selecting "Replace existing template" while updating your CloudFormation Stack. You must select a version number with the same major version as your current template.

**Note:** Updating an existing stack from template version v1.X.X -> v2.X.X is not supported. If you are on v1.X.X and wish to migrate to v2.X.X, it will involve a service disruption. To migrate, delete your original stack and recreate a new stack with the v2.X.X template.
Deleting the v1 stack will delete your Datadog integration for this account, stopping AWS data collection in Datadog temporarily. Collection will resume once the v2.X.X stack is successfully created.

## Datadog::Integrations::AWS

This CloudFormation stack only manages *AWS* resources required by the Datadog AWS integration. The actual integration configuration within Datadog platform can also be managed in CloudFormation using the custom resource [Datadog::Integrations::AWS](https://github.com/DataDog/datadog-cloudformation-resources/tree/master/datadog-integrations-aws-handler) if you like.
